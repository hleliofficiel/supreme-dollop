Beginner-Friendly Installation Guide

Setting up NovaQR does not require Git knowledge or complex terminal commands. Follow these 4 simple steps to open and run the app in Android Studio:

Step 1: Extract Downloaded Package

Unzip the downloaded package file (e.g., NovaQR_App_Full_Source_Code.zip) on your computer. Inside, you will find the main project folder NovaQR.

Step 2: Open Project in Android Studio

  1. Launch Android Studio on your machine.
  2. On the welcome screen, click Open (or go to File > Open).
  3. Browse to the extracted NovaQR project directory and click OK.
  4. Wait 1–2 minutes while Android Studio automatically downloads dependencies and performs Gradle Sync.

Step 3: Create & Configure Your .env Credentials File

  1. In the left-hand Project explorer, locate the file named .env.example in the project root.
  2. Duplicate or rename it to create a new file named .env (with a leading dot).
  3. Paste your own credentials for Supabase, Google Cloud Web Client ID, and Gemini API Key:
SUPABASE_URL=https://your-project-ref.supabase.co
SUPABASE_ANON_KEY=your_supabase_anon_key
GEMINI_API_KEY=your_gemini_api_key
GOOGLE_LOGIN_KEY=your_web_client_id.apps.googleusercontent.com

Step 4: Run the Application

  1. Connect a physical Android phone via USB with USB Debugging enabled, OR start an Android Virtual Device (Emulator).
  2. Click the green Run 'app' button (Play icon) in the top toolbar of Android Studio.
  3. Your app will compile and launch immediately on the device!

Step 5: App Evaluation & Guest Access

For instant evaluation during setup, tap "Continue as Guest" on the welcome screen or register a new test account directly within the application. No pre-configured login credentials required.

Application Assembly & APK Build Guide

Learn how to compile, assemble, and export signed Android binaries (APK and AAB) after making code or asset modifications.

Two Output Formats: APK vs AAB

APK (.apk): Android Package file used for direct device installation, side-loading, website downloads, or beta distribution.
AAB (.aab): Android App Bundle used strictly for uploading and publishing to the official Google Play Console.

1. Assembling a Debug APK (Instant Testing)

To compile a debug binary for local testing without keystore signing setup, run this Gradle command in Android Studio Terminal:

./gradlew assembleDebug

Output File Path: app/build/outputs/apk/debug/app-debug.apk

2. Configuring Release Keystore Signing

Before assembling a production Release APK or Play Store Bundle, configure your release keystore inside app/build.gradle.kts:

android {
    signingConfigs {
        create("release") {
            storeFile = file("your-release-key.jks") // Place your .jks file in project root or app folder
            storePassword = "YOUR_KEYSTORE_PASSWORD"
            keyAlias = "YOUR_KEY_ALIAS"
            keyPassword = "YOUR_KEY_PASSWORD"
        }
    }
    buildTypes {
        getByName("release") {
            isMinifyEnabled = true
            isShrinkResources = true
            proguardFiles(getDefaultProguardFile("proguard-android-optimize.txt"), "proguard-rules.pro")
            signingConfig = signingConfigs.getByName("release")
        }
    }
}

3. Assembling a Production Release APK

To compile the optimized, production-ready Release APK file, execute:

./gradlew assembleRelease

Output File Path: app/build/outputs/apk/release/app-release.apk

4. Assembling an Android App Bundle (.aab) for Google Play

To generate the official App Bundle binary required by Google Play Console:

./gradlew bundleRelease

Output File Path: app/build/outputs/bundle/release/app-release.aab

5. Obtaining the Ready APK via Android Studio GUI (No Terminal Required)

If you prefer using the Android Studio graphic interface instead of terminal commands:

  1. In the top menu bar, click Build > Build APK(s) / Bundle(s) > Build APK(s).
  2. Wait for Android Studio to finish compiling (a pop-up notification will appear at the bottom right).
  3. Click the blue locate link inside the notification pop-up.
  4. Android Studio will automatically open your operating system file manager directly to the folder containing your compiled, ready app-debug.apk or app-release.apk!

Google Authentication Specification

NovaQR implements modern dual-layer Google Authentication architecture on Android. The system attempts primary authentication via native on-device Google CredentialManager, falling back smoothly to Browser OAuth 2.0 with custom deep links when required.

1. Authentication Architecture

Native CredentialManager (Primary)

Invokes Android's native bottom-sheet account picker. Retrieves a cryptographically signed Google ID Token directly within the app and passes it to Supabase Auth without opening external browser windows.

Browser OAuth 2.0 (Fallback)

If CredentialManager is unsupported on older Play Services versions, the app opens Chrome Custom Tabs to complete OAuth authorization, returning via deep link com.example.novaqr://callback.

2. Google Cloud Console Provisioning

To enable Google Authentication for your build, set up your OAuth parameters in Google Cloud Console:

  1. Log into Google Cloud Console and create or select your project.
  2. Navigate to APIs & Services > OAuth consent screen.
  3. Set User Type to External and fill in required app contact details.
  4. Configure mandatory authorization scopes:
    • openid
    • https://www.googleapis.com/auth/userinfo.email
    • https://www.googleapis.com/auth/userinfo.profile
  5. Publish your consent screen status to In Production or register developer emails under Test Users.
  6. Navigate to Credentials > Create Credentials > OAuth client ID.
  7. Select Web application (This Web Client ID will be used as GOOGLE_LOGIN_KEY in Supabase and .env).

3. Generating Required SHA Fingerprints

Google CredentialManager requires linking your Android app's signing certificate fingerprints (SHA-1 and SHA-256) to an Android Client ID entry in Google Cloud Console.

Generating Debug SHA Fingerprints via Terminal:

# Linux / macOS
keytool -list -v -keystore ~/.android/debug.keystore -alias androiddebugkey -storepass android -keypass android

# Windows
keytool -list -v -keystore "%USERPROFILE%\.android\debug.keystore" -alias androiddebugkey -storepass android -keypass android

# Alternatively via Gradle inside project:
./gradlew signingReport

Copy both SHA-1 and SHA-256 keys and paste them into your Android Client ID configuration in Google Cloud Console under matching package name com.example.novaqr.

4. Redirect URI Whitelisting in Supabase

To accept deep link redirects from Browser OAuth, register your custom schemes in Supabase Dashboard > Authentication > URL Configuration > Redirect URLs:

com.example.novaqr://callback
novaqr://callback

5. Environment Variables Configuration

Add your Web Client ID and Redirect scheme to your project .env file:

GOOGLE_LOGIN_KEY=YOUR_GOOGLE_WEB_CLIENT_ID.apps.googleusercontent.com
GOOGLE_CUSTOM_REDIRECT_URL=com.example.novaqr://callback

Supabase Database & Security Policies

NovaQR relies on Supabase PostgreSQL for persistent user storage, saved QR code history, dynamic remote agent configuration, user plan management, and in-app system alerts.

Critical Security Alert: Resolving Table Publicly Accessible (rls_disabled_in_public)

If you receive an email or notification from Supabase warning about "Table publicly accessible (rls_disabled_in_public)", do not panic! This occurs when new tables are created without enabling Row-Level Security (RLS).

Resolution Steps: Copy and run the complete SQL script below inside your Supabase Dashboard > SQL Editor. This enables RLS across all tables and restricts access so users can only read/write their own records.

1. Complete Database Schema Setup & RLS Policies

Execute this complete SQL initialization script in Supabase Dashboard > SQL Editor to automatically construct all 7 required tables, indexes, triggers, and Row-Level Security (RLS) policies:

-- 1. Create User Profiles Table (with plan expiry & trial metadata)
CREATE TABLE IF NOT EXISTS public.profiles (
  id uuid REFERENCES auth.users ON DELETE CASCADE PRIMARY KEY,
  email text,
  full_name text,
  plan text DEFAULT 'free', -- Options: 'free', 'pro', 'enterprise'
  plan_expires_at timestamp with time zone,
  is_trial boolean DEFAULT false,
  avatar_base64 text,
  created_at timestamp with time zone DEFAULT timezone('utc'::text, now())
);

ALTER TABLE public.profiles ENABLE ROW LEVEL SECURITY;
CREATE POLICY "Users can view own profile" ON public.profiles FOR SELECT USING (auth.uid() = id);
CREATE POLICY "Users can insert own profile" ON public.profiles FOR INSERT WITH CHECK (auth.uid() = id);
CREATE POLICY "Users can update own profile" ON public.profiles FOR UPDATE USING (auth.uid() = id);

-- 2. Automatic User Profile Creation & Default Plan Trigger
CREATE OR REPLACE FUNCTION public.handle_new_user()
RETURNS trigger AS $$
BEGIN
  INSERT INTO public.profiles (id, email, full_name, plan, plan_expires_at, is_trial)
  VALUES (
    new.id,
    new.email,
    COALESCE(new.raw_user_meta_data->>'full_name', split_part(new.email, '@', 1)),
    'free', -- Set to 'pro' if you want a 100% free app for all users
    NULL,   -- e.g. NOW() + INTERVAL '30 days' for an automatic $0 30-day Pro trial
    false
  )
  ON CONFLICT (id) DO NOTHING;
  RETURN new;
END;
$$ LANGUAGE plpgsql SECURITY DEFINER;

DROP TRIGGER IF EXISTS on_auth_user_created ON auth.users;
CREATE TRIGGER on_auth_user_created
  AFTER INSERT ON auth.users
  FOR EACH ROW EXECUTE FUNCTION public.handle_new_user();

-- 3. Saved QR Code Vault Table
CREATE TABLE IF NOT EXISTS public.saved_qrs (
  id SERIAL PRIMARY KEY,
  title text NOT NULL,
  content text NOT NULL,
  type_name text NOT NULL,
  timestamp bigint NOT NULL,
  is_favorite boolean NOT NULL DEFAULT false,
  style_json text NOT NULL,
  user_id uuid REFERENCES auth.users NOT NULL DEFAULT auth.uid()
);

ALTER TABLE public.saved_qrs ENABLE ROW LEVEL SECURITY;
CREATE POLICY "Users can view own qrs" ON public.saved_qrs FOR SELECT USING (auth.uid() = user_id);
CREATE POLICY "Users can insert own qrs" ON public.saved_qrs FOR INSERT WITH CHECK (auth.uid() = user_id);
CREATE POLICY "Users can update own qrs" ON public.saved_qrs FOR UPDATE USING (auth.uid() = user_id);
CREATE POLICY "Users can delete own qrs" ON public.saved_qrs FOR DELETE USING (auth.uid() = user_id);

-- 4. Broadcast System Notifications Table (Global App Alerts)
CREATE TABLE IF NOT EXISTS public.app_notifications (
  id SERIAL PRIMARY KEY,
  title text NOT NULL,
  message text NOT NULL,
  type text DEFAULT 'info', -- 'info', 'promo', 'update', 'alert'
  action_url text,

2. User Account Management Guide

Supabase provides built-in user administration tools through both the web dashboard and SQL commands:

  • Viewing Registered Users: Navigate to Supabase Dashboard > Authentication > Users to search, filter, or view all signed-up accounts.

Monetization, Revenue Model & Subscription Plans Guide

How App Owners Collect Revenue from Source Code

NovaQR is engineered as a commercial micro-SaaS application. All subscription revenue generated when end-users upgrade to the Pro Studio plan flows directly into your bank account or payment processor. No revenue shares or commission cuts are taken by the source code!

1. Revenue Generation Channels

A. Google Play Billing (Subscriptions)

End users pay via Google Play payment methods (Credit Card, Play Balance, PayPal). Google processes payouts directly into your linked developer bank account (85%–90% net revenue to app owner).

B. Direct Web Payment Gateway (PayPal / Stripe)

2. Setting Up Automatic $0 Trial & Plan Expiry in Supabase

To implement an automatic $0 trial or automated plan upgrade linked to database expiration dates, update the handle_new_user() trigger in Supabase SQL Editor:

-- Trigger function for Automatic $0 30-Day Pro Trial on User Signup:
CREATE OR REPLACE FUNCTION public.handle_new_user()
RETURNS trigger AS $$
BEGIN
  INSERT INTO public.profiles (
    id, 
    email, 
    full_name, 
    plan, 
    plan_expires_at, 
    is_trial
  )
  VALUES (
    new.id,
    new.email,
    COALESCE(new.raw_user_meta_data->>'full_name', split_part(new.email, '@', 1)),
    'pro',                            -- Grants Pro plan automatically ($0 trial)
    NOW() + INTERVAL '30 days',       -- Sets plan expiry date 30 days in future
    true                              -- Marks user as active trial participant
  )
  ON CONFLICT (id) DO NOTHING;
  RETURN new;
END;
$$ LANGUAGE plpgsql SECURITY DEFINER;

Frequently Asked Questions (FAQ)

Comprehensive self-service solutions categorized by sub-system.

Google Authentication & OAuth

Q: How does Google CredentialManager differ from standard Browser OAuth?

Answer: Google CredentialManager provides native, zero-redirect authentication directly within Android. It presents a native system UI, retrieves a signed ID Token, and verifies it with Supabase without leaving the app. Browser OAuth serves as a fallback for older devices.

Q: Why is SHA-1 and SHA-256 configuration mandatory for Google Sign-In?

Answer: Google Play Services validates the calling APK's digital signature against the registered SHA fingerprints in Google Cloud Console to prevent unauthorized apps from spoofing your OAuth Web Client ID.

Supabase & AI Engine

Q: Which Gemini AI models are supported in NovaQR v2.0?

Answer: NovaQR supports gemini-3.6-flash for ultra-fast response generation and gemini-3.1-pro for advanced reasoning. You can configure active models via .env or remotely in Supabase agent_config.

Internationalization, RTL & Release Signing

Q: Does NovaQR support Arabic and Right-to-Left (RTL) screen layouts?

Answer: Yes! Jetpack Compose layouts in NovaQR utilize logical padding and alignment properties, making them fully compatible with Arabic, Persian, and Hebrew RTL rendering.

Q: How do I generate an Android App Bundle (.aab) for Google Play Store publication?

Answer: Execute ./gradlew bundleRelease via terminal after configuring your signing keystore credentials inside app/build.gradle.kts.
